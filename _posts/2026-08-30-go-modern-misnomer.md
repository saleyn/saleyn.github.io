I keep seeing "Go is a modern language" in job postings, conference talks, and blog posts, and I keep having the same reaction: modern in what exactly?

The answer, if you actually look, is "modern tooling." And that's the part that falls apart first.

`gofmt` is the usual example. One style, zero config, ships with the toolchain. Sounds clean. But [clang-format](https://clang.llvm.org/docs/ClangFormat.html) has been part of Clang since 2014, it's the default compiler on macOS, and it's *more* flexible - configurable per-project, multiple style presets, handles C, C++, and Objective-C. Add `clang-tidy`, CMake, Conan, vcpkg, sanitizers, and the C++ tooling ecosystem has closed most of the gap that made "Go has a build system and C++ has prayer" sound like a fair comparison in 2012. It doesn't anymore.

The one thing `gofmt` genuinely has over `clang-format` is the "zero arguments, one style, no debate" property. That's a real team-ergonomics win. But it's a simplicity feature, not a modernity one, and it's one tool, not a toolchain revolution. So the "modern tooling" pillar of the "Go is modern" claim is thinner than people give it credit for.

The language itself is doing something pretty specific, and it's not "tracking the state of the art." It's pushing back against it.

Take concurrency. Go's model is CSP. Hoare published that in 1978. The field has moved on - actors, structured concurrency, async/await, dataflow languages - and Go's answer to all of that is "channels are enough." Fine, for I/O-bound network servers. But the scheduler doesn't even guarantee fairness. [Ian Lance Taylor said this pretty directly on golang-nuts](https://groups.google.com/g/golang-nuts/c/KDqeQp2jOgA): the scheduler is "not optimized for fairness." It's tuned for the case where each goroutine does a little work, hits the network, and yields. If you've got CPU-bound goroutines of wildly different cost, you get uneven distribution. That's not a bug, it's the design. But Erlang has had a hard round-robin reduction-based fairness guarantee since the '80s. So Go's concurrency story is actually *older* than Erlang's in the ways that matter for mixed workloads.

Then there's metaprogramming. There isn't any. No macros, no compile-time codegen, no templates. The [Go FAQ](https://go.dev/doc/faq) says this out loud: "C++ supports template metaprogramming; Go does not." Other languages shipped this stuff a decade ago and it's table stakes now. Go's position is that you shouldn't need it, and that the lack of it means the code is more readable. I get the argument. I also think "we chose not to have this" is not the same as "this is modern."

Functional features are a similar story. You get first-class functions and closures. That's the whole list. No pattern matching, no ADTs, no type-driven development. In 2026, that's not a controversial gap - it's just... not there.

Generics showed up in [Go 1.18](https://go.dev/blog/intro-generics), which was 2022. Scala and Rust had them well before that, and C++20 shipped them in 2020. Go's version is also a deliberately limited instantiation-based design, which is fine for what it is, but "we got generics 13 years late and made them smaller" is not a modernity claim.

The error handling thing is the one that gets people the most. `if err != nil { return err }` appears thousands of times in a non-trivial codebase. There's no ternary, no `?` operator, no default arguments, no string interpolation. The team got a lot of proposals for a `?` operator in 2024-2025 (the [most prominent one filed by Ian Lance Taylor himself in January 2025](https://github.com/golang/go/discussions/71460)), and in June 2025 they basically said ["we're not doing this"](https://golangweekly.com/issues/556). That's a design decision. It's also a decision that makes the language significantly more verbose than alternatives for equivalent functionality, and calling that "simplicity" is doing a lot of work.

And there's a newer angle on this that didn't exist when the language was designed. In 2026, a meaningful share of code is read, generated, and refactored by LLMs, and token count is a real cost - not just in API bills but in context window. A [RosettaCode-based benchmark](https://rosettacode.org/) using GPT-family tokenization puts Go at roughly 182 tokens for a standard set of tasks. For comparison: Haskell sits at ~130, Python at ~128, Clojure at ~109, Ruby at ~119. Go is in the bottom third. That's not a rounding error. If 80% of your agent's context window is code - which is the realistic number for a non-trivial codebase - then Go is eating a significantly larger share of that window for the same logical content. The practical effect: fewer files fit in context, the model has less room to reason about the surrounding system, and you hit context limits sooner. One developer on [Lobsters](https://lobste.rs/s/nx9uwg/which_programming_languages_are_most) put it bluntly in January 2026: "Golang certainly is very verbose which is pretty bad for LLMs once you want it to understand a lot and not just a single file."

Now, there's a counterargument, and it's not silly. Google's own engineering blog published [a piece in August 2026](https://developers.googleblog.com/why-go-is-an-ideal-language-for-ai-assisted-software-engineering/) arguing that Go's *consistency* - one style, one way to do things, no clever abstractions - makes AI output *more predictable* even if it's *more verbose*. The claim is that a model is less likely to hallucinate a Rust lifetime or a C++ template specialization than it is to get a Go `if err != nil` block wrong. And there's some evidence for this: Go's training corpus is enormous and stylistically uniform, which means the model has a very narrow distribution to sample from. But "predictable" and "efficient" are different properties, and the token cost is real. You're paying more context to get a narrower output distribution. Whether that trade is worth it depends on your failure mode - if your main risk is the model generating subtly wrong code, Go's constraint helps. If your main risk is running out of context in a large codebase, it hurts. Either way, the verbosity that the Go team frames as "simplicity" has a concrete, measurable cost in the AI era that didn't exist in 2009, and it's a cost that gets worse as codebases grow, not better.

And the token cost is just the tip of it. The broader development cost story is where Go's verbosity stops being a style argument and starts being a line item.

For a comparable set of backend features - a REST API with auth, database access, background jobs, and basic observability - the relative code volume is roughly: Python at 1x, Elixir at ~1.1x, Go at ~1.5x, Rust at ~1.8x, C++ at ~2.5x. That's not a precise number, but it's the consistent shape you see across codebases that implement the same spec. Go sits in the middle, but the "middle" is doing a lot of work. Compared to Python or Elixir, you're writing 40-50% more code for the same functionality, and most of it is the `if err != nil` tax plus the lack of default arguments, the lack of destructuring, the lack of pattern matching on return types. Compared to Rust, you're writing less, but Rust's verbosity buys you compile-time guarantees that eliminate an entire class of runtime bugs, so the "less code" advantage is partially illusory.

The developer velocity story is similar. Go's selling point has always been "easy to learn, fast to hire." And that's true - the learning curve is gentler than Rust's, and the job market is bigger than Elixir's. But "easy to learn" and "fast to build" are different things. The Go team's own 2024 developer survey flagged error handling as the top friction point. StackShare's community data shows "you waste time in plumbing code catching errors" as the most upvoted con (43 votes), ahead of "verbose" (25). That's not a small thing. If a meaningful fraction of your development time is spent writing and reviewing boilerplate error plumbing, your velocity is lower than the "Go is fast to develop" narrative implies. Python and Elixir developers hit that friction less often, not because their code is more correct, but because the language doesn't force you to handle every error at every call site.

Elixir is the interesting comparison here because it's the one language that is *both* more concise *and* more capable in the areas Go is weak. You get pattern matching, algebraic data types (via structs and keyword maps), hot-loading, always-on observability, and a fair scheduler, in fewer lines of code. The trade is that Elixir's ecosystem is smaller and the job market is thinner. The GC story, if anything, leans the other way: [BEAM's per-process GC](https://www.erlang.org/doc/apps/erts/garbage_collection.html) means a pause in one process is invisible to all others, and the [fair scheduler](https://www.erlang.org/doc/apps/erts/scheduler.html) guarantees no process starves while another is collecting. Go's GC is global - every STW phase stops every goroutine - so under sustained load, pause timing is a system-wide property you can't reason about per unit. For a team of 3-10 building a concurrent, long-running service, the Elixir development cost is often *lower* than Go's, not higher, once you account for the observability and fault-tolerance infrastructure you'd otherwise have to bolt on.

C++ is the other end of the spectrum. You can write less code than Go for performance-critical paths, but the development cost is dominated by build times, memory management, and the sheer cognitive load of the language. A C++ codebase that Go developers find "complex" is often the *same* logic in fewer lines, but with a maintenance cost that's 2-3x higher per engineer-month. Go's pitch against C++ is real, but it's a pitch against a specific failure mode (C++ complexity), not a claim that Go is the cheapest language to develop in.

Rust is the same story from the other direction. More code than Go, but the code is more correct. The compiler catches bugs that Go would ship to production. The development cost is front-loaded in the learning curve (the ownership model is genuinely hard, and the compiler error messages, while improving, are still a tax), but the maintenance cost is lower over the lifetime of the project. For a long-lived system, Rust's total cost of ownership is often competitive with Go's, even if the initial velocity is slower.

So where does that leave you? Python gets you to a working prototype the fastest, but the dynamic typing means you pay for it later in debugging and refactoring, and it falls apart at the concurrency scale that Go and Elixir handle comfortably. Elixir is the best total cost for concurrent, long-running services - the BEAM handles fault tolerance, observability, and fair scheduling for you, so you're not bolting any of that on. Go is the middle option: more code than Elixir, less than Rust, with a maintenance cost that's dominated by error plumbing rather than memory safety or build complexity. Rust is the front-loaded bet - you pay in learning curve and initial velocity, but the compiler catches a class of bugs that Go would ship to production, and the long-term maintenance cost is the lowest of the group. C++ is only in this conversation because Go's original pitch was "we're the C++ alternative," and the honest answer is that C++'s development cost is the highest of all five, but it's a cost you only pay if you need what C++ gives you that nothing else does.

Go is in the middle. That's not a bad position. But "in the middle" is not "modern," and it's not "the best development cost." It's a reasonable default, which is a different claim than the one the "modern language" label is making.

Then there's the thing nobody talks about enough: observability. In Go, you want to see what a running system is doing and you import `net/http/pprof`, expose a port, and hope for the best. You want tracing? Wire up OpenTelemetry. You want to inspect a goroutine's state at runtime? You can dump a stack trace, but you can't poke at it. You want to hot-swap a function in a running system? No.

In Erlang, every single process is inspectable by default. [`erlang:process_info/2`](https://www.erlang.org/doc/man/erlang.html#process_info-2) gives you the mailbox, the stack, the message queue, memory usage - on a live, running, production system, with zero setup. You can trace any function call with [`erlang:trace_pattern/3`](https://www.erlang.org/doc/man/erlang.html#trace_pattern-3) and it's always available. You can hot-load a new module into a running node. The runtime *is* the observability layer. In Go, observability is a feature you add. That's a fundamentally different architectural bet, and it's the older one.

So if you line up the actual language features - concurrency model, scheduler semantics, metaprogramming, functional expressiveness, generics timeline, conciseness, AI-era token efficiency, runtime introspection - Go is behind the field on most of them. The tooling story, which is supposed to be the saving grace, is also narrower than it looks once you account for what Clang and the broader C++ ecosystem have shipped. And the "modern" label lumps all of that together and lets the build tool carry the whole claim.

I don't think Go is a bad language. I think it's a coherent one, with a clear philosophy: small surface, static guarantees, fast builds, large-team readability. That's a legitimate set of priorities. But it's a 1970s set of priorities, and the "modern" label reframes the resistance to the field's direction as if it were leadership. It's not. It's a different bet, made in 2007, that has been very effective at marketing itself as the opposite of what it is.

The honest version is: Go is a deliberately conservative language with a decent toolchain. That's a complete and accurate description. "Modern language" is not.
